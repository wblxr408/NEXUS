# 最终答辩逐页内容规划

- 文档类型：答辩 PPT 内容蓝图（非实验结论）
- 建议版本：`defense_slides_v01`
- 建议页数：26 页正文 + 4 页备份页；现场时长约 12--15 分钟（正文），备份页仅在问答时使用
- 适用范围：FanciSwarm UWB + 视觉 + ROS2 的外部目标高精度定位项目
- 规划依据：`docs/PROJECT_INDEX.md`、`docs/无人机高精度目标定位项目规划 (2).md`、`docs/decisions/2026-08-18_ADR-002_target-localization-scope.md`
- 视觉依据：`defense/slides/PPT制作视觉风格.md`

## 使用规则

1. 本文是“每页应该说什么、需要什么证据”的清单，不把其中的指标或方案写成已完成事实。
2. 所有实测数字、实物图、录屏、运行截图和结论，必须填写对应的 `experiments/runs/YYYY-MM-DD_Exxx_<slug>` 与 `docs/records/evidence-index.md` 条目后，才可放入最终 PPT。
3. `目标值`、`外部参考`、`仿真/测试样例`、`实测值`、`已验证实现` 必须使用不同页脚标签；没有正式运行编号时只能使用 `REQUIREMENT`、`TARGET`、`REFERENCE` 或 `TBD`，`MEASURED` 必须关联运行编号，`IMPLEMENTED` 必须有可复现的构建/测试记录。
4. 被定位对象始终是**无人机之外的目标**。无人机是传感器、通信和计算平台；不能用 `base_link` 或飞控 `/odom_global_001` 直接代表目标位置。
5. 未确认的目标形态、UWB 标签安装对象、相机方案、桥接方式、外参、时间同步方式和真值方案均标为 `TBD`。不要为版面完整而补写事实。
6. 图表文件按 `fig_<topic>_<condition>_vNN.<ext>` 命名，表格按 `tbl_<topic>_vNN.csv` 命名；每张图在 PPT 备注中登记运行编号、坐标系、单位、样本数和生成脚本版本。

## 叙事主线与页脚标记

叙事顺序为：**赛题要求 → 问题与边界 → 已部署的软件/硬件基础 → 感知与坐标链 → 算法与融合 → 验证方法 → 实测证据 → 演示交付**。这样既逐项回应题目要求，也避免把软件安装或架构设计误说成定位精度成果。

| 页脚标记 | 含义 | 允许使用的内容 |
|---|---|---|
| `REQUIREMENT / 赛题要求` | 要求本身 | 题目条目、验收交付物 |
| `IMPLEMENTED / 已实现` | 代码、环境或接口已完成 | 构建/测试命令、版本、日志；仍需运行编号或可复现记录 |
| `MEASURED / 实测` | 正式实验结论 | 仅限证据索引已登记且可重跑的运行 |
| `TARGET / 目标` | 项目冲刺或保底目标 | 不得与实测数字同样式呈现 |
| `REFERENCE / 外部参考` | 厂商或文献资料 | 明确来源，不能改写为本项目精度 |
| `TBD / 待确认` | 硬件到货后决定 | 接口、标定、测量模型等未决事实 |

### 01｜封面：UWB × Vision 的目标世界坐标定位

- **这一页回答**：我们要完成什么项目？
- **应讲内容**：项目名称、团队、答辩场景；一句话定义为“以无人机为移动感知/计算平台，利用 UWB 与视觉在 ROS2 中输出外部目标的世界坐标，并以可追溯实验验证”。
- **主视觉**：深石墨背景；左/右偏置无人机实物或技术渲染；四基站几何、相机视锥、`map` 坐标轴和一个高亮目标点汇聚到画面中部。标题占大面积留白。
- **需要填入**：`[项目正式名称]`、`[团队名称/成员]`、`[答辩日期]`、`[实物照片 A01 或经授权技术图]`。
- **页脚**：`REQUIREMENT / 项目概述`。不出现任何实测精度数值。

### 02｜目录：从赛题要求到可验证的定位结果

- **这一页回答**：接下来如何证明项目逐项满足要求？
- **应讲内容**：用 5 个段落串起汇报：任务与边界、系统与部署、定位方法、实验验证、演示交付。说明所有结果均以运行编号为索引。
- **主视觉**：一条从“不确定观测”流向“目标位置 + 误差”的细轨迹，标出 5 个章节节点；不用普通项目符号堆满页面。
- **需要填入**：`[答辩时长]`、`[章节页码，可在定稿后回填]`。
- **页脚**：`REQUIREMENT / 汇报结构`。

### 03｜赛题要求与本项目交付映射

- **这一页回答**：题目要求什么，我们分别交付什么？
- **应讲内容**：逐条列出并口头强调四项主要求：① ROS2 环境与自研节点；② UWB/视觉定位算法精度比较；③ 目标坐标转换；④ 演示应用。右侧给出对应交付：环境/代码与测试、对比实验报告、`/nexus/target/pose` 和标定记录、RViz2/视频与数据包。
- **主视觉**：四行“要求 → 可核验交付物”映射，使用编号和细连接线，不使用大卡片。此页是后续章节的验收索引。
- **需要填入**：`[赛题原文 A02]`、`[最终提交物版本/路径]`、`[每项对应证据索引行号]`。
- **页脚**：`REQUIREMENT / 赛题条目`；不要提前标绿色“已完成”。

### 04｜问题定义：定位谁、在什么坐标系中定位

- **这一页回答**：系统输出到底是什么，如何避免概念混淆？
- **应讲内容**：目标是无人机外部的 `target_link`，最终输出为 `map` 下的目标位置/位姿 `/nexus/target/pose`；`base_link` 仅代表无人机平台。说明两种待验证测量模型：目标直接测量，或平台位姿 + 机载视觉的间接测量；本次实验只能采用实际确认的一种并写明。
- **主视觉**：上半部“无人机 ≠ 目标”的简洁空间图；下半部两条可选测量链，未确认链用灰色虚线并标 `TBD`。
- **需要填入**：`[目标物形态]`、`[所采用测量模型]`、`[target_id 规则]`、`[决策记录编号]`。
- **页脚**：`TBD / 测量模型待硬件确认`，或在确认后替换为对应运行编号。

### 05｜场地与约束：为什么必须融合，而不是只依赖一种传感器

- **这一页回答**：真实沙盘场景带来哪些误差和机会？

- **主视觉**：顶视实拍/测绘图叠加薄线：蓝色为基站覆盖与可能多径区，青色为相机视场，橙色为遮挡区。若尚未测量，用“部署草案”而非“实际部署”。
- **需要填入**：`[场地长×宽×高，m]`、`[沙盘照片 A01]`、`[基站/相机候选点]`、`[现场约束记录]`。
- **页脚**：`MEASURED / 场地测量` 或 `TBD / 部署草案`，二者不可混用。

### 06｜硬件与分层角色：飞控基础、UWB、视觉和计算平台

- **这一页回答**：已经选定或待确认的硬件分别做什么？
- **应讲内容**：Mcontroller V7 负责实时飞控闭环；FanciSwarm 四基站 + 标签提供官方 UWB 基线；相机作为视觉输入但具体型号/数量待确认；树莓派/兼容主机承担 ROS1 硬件侧，ROS2 主机承担算法与可视化。UM982 仅为室外可选参考，不是室内主定位。
- **主视觉**：一个从“传感器”到“计算平台”的剖面式装配图，明确已确认部件与 `TBD` 部件。UWB 采用蓝色锚点，视觉采用青色视锥。
- **需要填入**：`[实际设备清单/版本]`、`[标签安装对象]`、`[相机型号/帧率/接口]`、`[硬件照片 A01]`。
- **页脚**：已确认硬件用 `REFERENCE / 官方基线`；实际到货、接线与使用状态另用 `MEASURED / 验收运行编号`。

### 07｜为什么需要双 ROS：ROS1 硬件兼容与 ROS2 二次自研

- **这一页回答**：为什么不是只用一种 ROS？
- **应讲内容**：官方 `fcu_core` 的兼容基线是 Ubuntu 20.04 + ROS1 Noetic；赛题要求 ROS2，自研视觉、目标定位、坐标转换、评估和展示都放在 Ubuntu 22.04 + ROS2 Humble。两侧独立运行、显式通信，不强行混装。强调 ROS2 是验收中的自研主线。
- **主视觉**：左右两个操作环境，中央为桥接契约；左侧只保留硬件状态，右侧以目标观测和目标输出为焦点。用实线表示确定职责，桥接实现未定时使用虚线。
- **需要填入**：`[ROS1 主机/容器信息]`、`[ROS2 主机信息]`、`[实际 bridge 方案]`、`[网络/USB 连接状态]`。
- **页脚**：`REFERENCE / 官方兼容基线` + `TBD / bridge 方式`；实机联调后追加运行编号。

### 08｜ROS2 环境搭建：赛题要求的可复现软件基础

- **这一页回答**：ROS2 是否真正安装、配置并可复现？
- **应讲内容**：这是独立验收页，不能一句带过。展示 Ubuntu 22.04、ROS2 Humble、工作空间和自研包；说明按顺序执行依赖安装、`colcon build --symlink-install`、`colcon test`、`colcon test-result --verbose`。讲清“环境完成”与“精度达标”是两件事。
- **主视觉**：左侧为精简终端记录/构建流水线，右侧为 5 个 ROS2 包的结构图：`nexus_msgs`、`nexus_vision_localization`、`nexus_coord_transform`、`nexus_fusion_localization`、`nexus_bringup`/`nexus_viz_dashboard`。
- **需要填入**：`[Ubuntu 版本]`、`[ROS_DISTRO]`、`[colcon list 截图]`、`[build/test 命令输出截图]`、`[依赖版本]`、`[构建测试运行编号]`、`[提交版本/commit]`。
- **页脚**：未提供可复现日志时用 `TBD / 待构建验证`；有日志后用 `IMPLEMENTED / [运行编号]`。不得以代码目录截图替代测试证据。

### 09｜ROS2 自研软件链：从观测消息到目标输出

- **这一页回答**：ROS2 中具体实现了哪些赛题相关能力？
- **应讲内容**：按数据语义讲：视觉节点产生 `TargetObservation`；坐标转换统一 frame/单位；融合节点产生 `/nexus/target/pose`；bringup/可视化负责启动、录包和展示。每条目标消息含采样时间、目标 ID、来源模式、协方差、置信度和米制单位。
- **主视觉**：单向数据流，而非“软件架构宣传图”；每个节点只保留输入、核心操作、输出三项。平台状态和目标观测使用不同形状或标签，防止误混。
- **需要填入**：`[实际包版本/节点名]`、`[message 定义版本]`、`[launch 文件]`、`[接口测试结果/运行编号]`。
- **页脚**：`IMPLEMENTED / 接口与测试`；若只是设计，必须写 `TBD / 接口草案`。

### 10｜信息通道：ROS1 到 ROS2 的数据、时间与语义

- **这一页回答**：跨 ROS 传输什么，如何保证其可解释？
- **应讲内容**：ROS1 `/odom_global_001`、`/imu_global_001` 作为平台状态送至 ROS2 `/nexus/fcu/odom`、`/nexus/fcu/imu`；它们不是目标位姿。展示 envelope 的 `schema_version`、序号、采样时间、frame、来源和 payload；区分采样时间与 ROS 接收时间。桥接技术选择由实测决定。
- **主视觉**：横向消息流与字段放大镜；标出厘米→米、轴向转换如有，必须发生在 ROS1 适配层且写明依据。
- **需要填入**：`[实际 topic/频率]`、`[frame]`、`[单位换算规则]`、`[延迟测量方法/结果]`、`[bridge 类型]`、`[联调运行编号]`。
- **页脚**：`TBD / 传输实现待定型`；完成后用 `MEASURED / 联调运行编号`，不能只写“通信正常”。

### 11｜坐标转换：传感器坐标如何成为目标世界坐标

- **这一页回答**：任务 3 的坐标转换具体如何做？
- **应讲内容**：展示 `sensor → camera_i/base_link → target_link → map` 的变换链；说明 `map` 原点、坐标轴、NED/ENU、单位和外参都必须以标定记录固定。直接测量模型和间接测量模型有不同链路，报告中只能画实验实际使用的那一条为实线。
- **主视觉**：一个三维坐标系、相机视锥、无人机机体系和目标标签平面；每个 frame 有小 XYZ 轴。转换为旋转 `R` + 平移 `t` 的最小公式即可。
- **需要填入**：`[map 原点定义]`、`[右手/左手系]`、`[NED/ENU 约定]`、`[外参文件版本]`、`[单位]`、`[标定运行编号]`。
- **页脚**：`TBD / 标定前草案` 或 `MEASURED / 标定运行编号`；未测量时不能画带数值的坐标轴。

### 12｜UWB 基线：四基站几何与官方位置输出的验证

- **这一页回答**：UWB 在本项目中承担什么角色，怎样验证？
- **应讲内容**：UWB 用作室内绝对位置基线；四基站位置先测量和记录，再以 GDOP/静态误差辅助选择部署。强调厂商“<10 cm”仅为外部资料，项目要报告自己的 RMSE、CEP95、更新率和误差热力图。若无法获得原始测距，则只比较可获取的官方位置输出，不虚构 Chan/Taylor/TDOA 比较。
- **主视觉**：顶视四锚点、量测圆弧与覆盖/GDOP 图；右侧预留“官方基线 vs 项目实测”两列，项目列为空数据占位直到实验完成。

### 13｜视觉定位：目标识别、相机标定与位姿求解

- **这一页回答**：视觉如何从像素得到目标观测？
- **应讲内容**：说明相机输入经过 AprilTag/ArUco 检测、内参/外参、PnP 或多相机三角测量生成带协方差的目标观测。多相机只在同步原始帧可获得时启用；否则以单相机方案作为已验证路线。不要把相机能力、标定精度写成既成事实。
- **主视觉**：青色相机视锥投向标签平面，局部放大角点与重投影残差；多相机路线以条件虚线表示。
- **需要填入**：`[相机数/型号]`、`[分辨率、fps、快门]`、`[标签家族/尺寸]`、`[内外参版本]`、`[重投影误差]`、`[视觉实验运行编号]`。
- **页脚**：`TBD / 相机输入待确认` 或 `MEASURED / 视觉运行编号`。若无真实帧，不展示“检测成功”截图。

### 14｜算法比较设计：以同一真值与口径选择方案

- **这一页回答**：任务 2 的“算法精度比较”怎么做到公平？
- **应讲内容**：列出对比组：官方 UWB、单目视觉 PnP、可用时的多相机三角测量、融合方案。所有组使用同一测试点/轨迹、同一 `map`、同一采样规则和同一真值来源；指标包括 RMSE、CEP50、CEP95、最大误差、有效样本数、更新率、延迟、遮挡连续性。接口能力不支持的算法明确“不纳入比较”。
- **主视觉**：实验矩阵：行是方法、列是静态/动态/遮挡与各评价指标；没有结果的格子标“待运行”，而不是填零。
- **需要填入**：`[真值测量工具与不确定度]`、`[测试点数量]`、`[轨迹类型]`、`[采样时长]`、`[纳入算法]`、`[统一评估脚本版本]`。
- **页脚**：`REQUIREMENT / 算法比较设计`；若为实测结果表则每行另标运行编号。

### 15｜融合方法：让多源观测的不确定性收缩

- **这一页回答**：融合究竟做了什么，为什么有可能改善稳定性？
- **应讲内容**：UWB 与视觉先做空间对齐、时间对齐和观测质量检查，再按协方差/置信度加权输出目标估计；单源有效时保持来源模式，双源有效时融合。第一版不替换飞控实时 EKF，也不把 ROS2→ROS1 回传当验收前提。
- **主视觉**：用大/中/小三组置信椭圆呈现 UWB、视觉、融合后的不确定度收缩；下方细链路标注 `alignment → confidence → weighted estimate`。不使用“两个方框加一个方框”的泛化图。
- **需要填入**：`[实际融合公式/算法名称]`、`[协方差或置信度来源]`、`[时间对齐窗口]`、`[过期阈值]`、`[代码/测试运行编号]`。
- **页脚**：`IMPLEMENTED / 单元测试` 不等于 `MEASURED / 融合精度`；两类标签分开。

### 16｜降级策略：遮挡或异常时定位不中断

- **这一页回答**：视觉或 UWB 质量下降时系统怎样处理？
- **应讲内容**：展示状态：正常双源 → 置信度下降 → 异常识别 → 降低对应权重 → 另一传感器接管 → 连续输出。只承诺已实施并测试的规则；如果尚未做 NLOS/遮挡实验，此页只作为设计与测试计划。
- **主视觉**：时间轴中的青色观测中断、蓝色基线持续、橙色告警段和最终连续轨迹；标题结论不能写“已稳定接管”，除非有运行证据。
- **需要填入**：`[视觉丢失判定]`、`[UWB 异常判定]`、`[权重/状态机规则]`、`[遮挡持续时间]`、`[连续性指标]`、`[异常测试运行编号]`。
- **页脚**：`TBD / 降级设计` 或 `MEASURED / 异常场景运行编号`。

### 17｜实验与真值：每一个误差数字从哪里来

- **这一页回答**：精度如何测量，测到的不是“看起来接近”吗？
- **应讲内容**：说明真值来源、真值坐标系、标定点布置、静态 8--10 点/动态轨迹/遮挡场景、采样时长和同步方式；误差定义为估计位置与真值位置在统一 `map` 系下的差。说明每个结论保留原始数据、配置、脚本版本和运行编号。
- **主视觉**：沙盘顶视图标出真值点、参考轨迹和测量点；右侧放误差向量定义与最小公式。此页比“结果页”更重要，讲清可信度来源。
- **需要填入**：`[真值方案]`、`[真值工具精度/不确定度]`、`[点位坐标表]`、`[样本数]`、`[时间同步方式]`、`[实验运行目录]`。
- **页脚**：`MEASURED / 实验设计运行编号`；真值方案未定则 `TBD`。

### 18｜指标与统计口径：不只报告一个“厘米数”

- **这一页回答**：如何判定定位方案是否更好？
- **应讲内容**：定义 RMSE、CEP50、CEP95、最大误差、更新频率、端到端延迟、有效样本数和异常/丢失率。说明按视觉主导、过渡、UWB 兜底等实际可解释区域分别统计，不把厂商参考值混入项目统计。
- **主视觉**：一个误差散点云、CEP 圆与一条带延迟标记的时间线；各指标只放定义和单位，不填虚构数值。
- **需要填入**：`[指标公式/脚本版本]`、`[分区规则]`、`[异常值处理规则]`、`[统计样本数]`、`[输出表 A11]`。
- **页脚**：`REQUIREMENT / 评价口径`，结果产生后在下一页使用 `MEASURED`。

### 19｜静态实验结果：多点误差分布与空间热力图

- **这一页回答**：在已知点位上，各方法的绝对误差如何？
- **应讲内容**：一句结论式标题必须由真实数据产生，例如“在 `[场景]` 中，`[方法]` 的 CEP95 为 `[数值] m`”；大图显示真值点、估计点、误差矢量与热力图；附小型指标表比较各方法。
- **主视觉**：一张大的沙盘顶视误差图。轨迹/点颜色严格按语义：UWB 蓝、视觉青、融合白/深色主线、误差橙；不要铺满多个小图。
- **需要填入**：`[运行编号]`、`[场景与日期]`、`[目标/标签安装方式]`、`[点位数]`、`[样本数]`、`[RMSE/CEP50/CEP95/最大误差]`、`[fig_static_error_*]`、`[tbl_static_metrics_*]`。
- **页脚**：`MEASURED / [运行编号] / [脚本版本]`。没有运行时用“静态结果页占位”，不得展示图形化假数据。

### 20｜动态实验结果：轨迹跟踪、更新率与延迟

- **这一页回答**：目标运动时系统能否持续输出且误差可量化？
- **应讲内容**：叠加参考轨迹与各方法估计轨迹，展示时间序列误差及更新率/延迟。结论应限定场景、速度与采样条件，避免从一条轨迹泛化到全场景。
- **主视觉**：左侧大轨迹叠加（直线、圆形或 8 字，取实际测试路线），右侧紧凑误差-时间曲线；视觉丢失或异常时以橙色细标记说明。
- **需要填入**：`[运行编号]`、`[轨迹类型/长度]`、`[目标速度，m/s]`、`[时长]`、`[同步规则]`、`[误差统计]`、`[Hz]`、`[延迟 ms]`、`[fig_dynamic_*]`。
- **页脚**：`MEASURED / [运行编号]`。

### 21｜遮挡与异常结果：从观测下降到连续输出

- **这一页回答**：困难条件下系统的降级表现是否被真实验证？
- **应讲内容**：选择一段有代表性的遮挡或 UWB 异常记录，按时间展示传感器有效性、融合权重/来源模式、目标输出和误差。只比较在相同异常定义下的数据；没有异常实验时删除“结果”措辞，保留为备选测试计划。
- **主视觉**：四层时间序列：观测可用性、置信度/权重、位置输出、误差；重点区域用低饱和橙色标识，视觉风格表达“降级”而非“崩溃”。
- **需要填入**：`[异常类型]`、`[起止时间]`、`[触发规则]`、`[单源接管时长]`、`[误差与丢失率]`、`[运行编号]`、`[fig_degradation_*]`。
- **页脚**：`MEASURED / [运行编号]`，否则移入备份页。

### 22｜结果汇总：按场景选择可解释的最终方案

- **这一页回答**：最终采用什么方案，证据支持到什么范围？
- **应讲内容**：只汇总已完成的静态、动态、遮挡运行，以“场景—推荐输出模式—RMSE/CEP95—更新率—证据编号”呈现。用一句审慎结论说明融合是否在特定场景下改善精度或连续性；不能以目标值替换统计结果。
- **主视觉**：一个紧凑的决策矩阵，突出最终选定行；右侧大号显示“已验证的核心指标”或“目标指标待验证”。
- **需要填入**：`[各场景运行编号]`、`[实际最终算法]`、`[指标表 A11]`、`[限制条件]`、`[未覆盖场景]`。
- **页脚**：`MEASURED / evidence-index 条目`。无完整证据时本页标题改为“验证计划与待补数据”。

### 23｜目标值、实测值与外部参考：边界清晰的指标声明

- **这一页回答**：我们对精度的表述是否严谨？
- **应讲内容**：明确三区：`TARGET`（例如视觉可见区冲刺 ≤5 cm、全场景兜底 <30 cm，均仅为规划目标）、`REFERENCE`（厂商 UWB 标称 <10 cm）、`MEASURED`（只填写本项目证据索引里的数值）。若实测尚无，第三列保留“待运行”，不要删除该列。
- **主视觉**：三列极简大数字/大占位符，三种标签清晰分离。`TARGET` 和 `REFERENCE` 用较低对比度；仅 `MEASURED` 获得高对比度焦点。
- **需要填入**：`[实测 RMSE/CEP95]`、`[场景]`、`[运行编号]`、`[厂商资料页码/链接]`、`[项目目标表述]`。

- **主视觉**：单张干净的 RViz2/仪表板实截图，标注少量关键区域；旁边为四步演示时间线。没有真实截图时只放线框占位，不模拟 UI。

### 25｜工程可交付性：可复现记录、分工与风险闭环
