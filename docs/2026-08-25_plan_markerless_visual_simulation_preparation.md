## 1. 先固定仿真边界

本阶段的目的，是在没有无人机、相机、UWB 基站和实机飞行的情况下，先验证“数据能生成、接口能回放、无标签视觉能输出相对目标位姿、坐标链能闭合、评估能复现”。仿真结果不能代替真实沙盘上的精度结果，也不能把渲染器的真值误写成实测值。

仿真主链路固定为：

```text
沙盘 3D 场景 + 无人机/目标轨迹
        ├─→ RGB 相机渲染 ─→ 无标签纯视觉 ─→ camera_i → target_link
        ├─→ 真值平台位姿 ─→ UWB 噪声/丢包模型 ─→ map → base_link
        └─→ 真值目标位姿 ───────────────────────→ 独立评估真值

map → base_link → camera_i → target_link
```

仿真中允许的传感器只有：

1. **UWB**：只模拟随无人机携带的标签，用于无人机自身 `base_link`；不得把它生成的结果标成沙盘目标位置。
2. **GNSS**：仅做室外/失效对照。室内沙盘的主实验将其标为 unavailable，不把虚拟经纬度作为主定位来源。
3. **纯视觉**：机载单目 RGB，不在目标上粘贴 AprilTag、ArUco 或其他人工标记。AprilTag 仍可作为以后工程对照，不进入本阶段无标签验收。

首版采用“轨迹驱动 + 离线渲染 + ROS2 回放”的仿真方式，而不是先做完整飞控 SITL。这样可先锁定算法、坐标和接口，减少尚未给出沙盘尺寸、相机实参和飞行动力学时引入的无关变量。待该链路通过后，再按需要接入 Gazebo/其他物理仿真器。

建议的工具分工如下；工具只是实现选择，不改变接口和验收边界：

| 工作 | 首选工具 | 产物 |
|---|---|---|
| 沙盘/目标建模 | Blender（或团队已有 CAD→mesh 工具） | 带单位、坐标原点和版本的 glTF/OBJ/PLY/原生工程文件 |
| 批量相机渲染 | Blender Python/BlenderProc；也可用已有 ROS2 仿真相机 | RGB 帧、相机真值、目标可见性/遮挡元数据 |
| 轨迹和噪声 | Python/NumPy，固定随机种子 | `trajectory.csv`、UWB/GNSS 合成流、噪声配置 |
| 算法回放 | ROS2 bag 或等价的文件回放适配器 | `Image`、`CameraInfo`、平台位姿和 `TargetObservation` |
| 评估与可视化 | 仓库现有 `code/analysis/` 工具、OpenCV、RViz2 | 指标 CSV、重投影图、TF/轨迹图和失败案例 |

若 Blender/BlenderProc 在当前机器上无法运行，可先用简化几何和 OpenCV 投影验证坐标、时间及消息链路；这只能算“几何仿真”，不能替代包含纹理、光照和遮挡的视觉仿真。

## 2. 必须先补齐的准备工作

### 2.1 明确两个定位对象

| 对象 | frame | 仿真真值 | 主观测 | 第一版定义必须填写 |
|---|---|---|---|---|
| 无人机自身 | `base_link` | 轨迹中的位置、姿态、速度 | UWB 标签到四基站的距离/平台 UWB 位置 | 机体参考点、标签安装点、机体轴向、允许飞行包络 |
| 沙盘外部目标 | `target_link` | 目标参考点和姿态 | 无标签 RGB 视觉 | 目标类别/ID、参考点、长宽高、是否固定、是否移动、是否有 CAD/纹理 |

当前“某种物体”尚未指定，不能直接选网络或声称可定位。先从沙盘中挑选一个代表目标，例如单栋建筑、圆柱设施或车辆模型，并填写 `target_spec.yaml`。目标必须满足以下至少一项可观测性：

- 有精确 CAD/网格和实际尺寸；或
- 无 CAD 但固定在沙盘中，具有足够稳定的纹理/几何，能建立三维地图；或
- 有可用于训练的目标模型、分割和关键点标注。

若目标无几何、无深度且无稳定纹理，单目无标签米制定位缺少尺度约束，应记录为数据条件阻塞，先补模型、尺寸、纹理或第二视角，不要通过更换网络掩盖问题。

### 2.2 对实体沙盘做可计量测量

图 1 只能说明布局形态（道路、建筑、树木、交通设施和中央区域），不能单独提供比例、绝对尺寸或深度真值。当前已收到一份尺寸/布局参数说明：沙盘外包络为 `4.0 m × 4.7 m`，中央工业核心区为 `2.0 m × 2.3 m`，其左下角暂定为 `(1.0, 1.2)`。这些值已写入 `simulation/sandbox_scene.yaml` 并作为 `metric_simulation` 的第一版基准。工业岛、储罐和外围建筑的许多坐标在参数说明中明确标为照片透视反推/估计，因此在模型中保留 `confidence` 和 `source`，不能把它们误当成测量仪器获得的独立真值。建模前仍需要：

1. 复核沙盘长、宽、台面高度、边界和可见区域；在固定位置建立 `P0/P1/P2` 三个物理基准点。当前外包络尺寸可直接使用，但不规则外边界的完整顶点仍待补充。
2. 规定 `map` 为右手系、单位 m、台面为 `z=0`、`+z` 向上；记录原点、`+x/+y` 方向和版本。
3. 测量目标、主要建筑、道路边界、中央设施和可作为验证点的角点；设计尺寸与实测尺寸分开记录。
4. 测量四个 UWB 基站的天线参考点、编号、安装高度、朝向和布局版本。未给出现场参数时，文件中留 `TBD`，不得使用固件示例坐标当现场真值。
5. 预留至少 8 个场景/目标标定点和 4 个独立验证点，覆盖近远、中心边缘和不同高度；验证点不能在调参后并回训练集。

每个尺寸和点位应记录测量工具、日期、重复测量差值和不确定度。若目标要验证厘米级，真值测量不确定度应明显小于该量级；仿真阶段应把此不确定度作为后续实测准入条件，而不是假设为零。

### 2.3 制作可追溯的 3D 沙盘模型

当前参数已落地为参数化模型目录 [`simulation/`](../simulation/)：`sandbox_scene.yaml` 是源配置，`generate_sandbox.py` 生成 `sandbox.obj`、`sandbox.sdf` 和 `sandbox_scene.json`。其中 SDF 面向已安装的 Gazebo Classic 11，JSON 保留给后续 Web 前端。模型包含道路、中央四个工业岛、储罐、外围建筑和树阵；交通灯、斑马线和不规则边界等尚未有完整坐标时，暂不虚构为精确物体。

本阶段对沙盘模型的要求分成两档。**如果目标是先做网页可视化、目标可见性检查、轨迹演示和坐标链联调，只要求沙盘内物体的相对比例、相对位置和遮挡关系正确，不要求真实绝对尺寸。** 可以把沙盘长边归一化为 1，或选择一个明确的仿真缩放因子 `S_scene`；所有建筑、道路、目标、无人机和基站都必须使用同一个缩放因子。此时模型只能称为 `layout_only`，不能据此报告米制定位精度、真实 UWB 测距精度或实体沙盘尺寸。

如果要验证单目算法的米制 6D 位姿、PnP 的尺度或逼真的 UWB 距离，则必须切换到 `metric_simulation`：至少补齐目标实际尺寸、相机焦距/内参、无人机和基站的相对距离，并在配置中明确单位为 m。两种模式使用同一套场景拓扑和相对位置，但不能混写实验结论。

模型不追求一次性“全场景完美”，先完成能支撑目标观测和遮挡关系的最小场景：

- 沙盘台面、边界和道路/建筑/植被/交通设施的几何体；
- 被定位目标的独立 mesh、`target_link` 原点和朝向；
- 目标和背景的材质、纹理、粗糙度、反光属性；
- 真实相机可见范围内的遮挡体、地面高度和碰撞几何；
- 低、中、高三个 LOD，避免渲染负载掩盖算法问题。

从实体照片获得的颜色和布局只能作为纹理/拓扑参考。每个模型资产登记 `asset_id`、来源、尺寸单位、坐标原点、版本、许可证和 SHA256；外部大文件放在 `data/`，Git 只登记位置和校验值。`layout_only` 模型还应登记 `scale_reference`（例如“沙盘长边=1.0”）和 `relative_layout_version`，便于将来整体换算到实测米制尺寸。

不安装 Blender 也可以完成第一版 `layout_only` 建模：用 Python/NumPy 根据 YAML 参数生成长方体、平面、圆柱体等基础几何，并导出 OBJ/PLY/glTF 和场景 JSON；网页队友以后加载这些模型即可。Blender 只在需要更真实的材质、光照、阴影、运动模糊和相机渲染时再安装，属于可选的后续渲染工具，不是场景数据的唯一来源。

建模顺序建议为“基准板/台面 → 大型建筑和道路 → 目标 → 植被与交通设施 → 材质和灯光”。导入或导出时只允许一次明确的单位换算；在 Blender 场景中显示 `map` 三轴和 1 m 标尺，并用三个已知点检查模型轴向。目标的 `target_link` 应作为独立空物体或节点导出，不能依赖 mesh 几何中心被工具自动猜测。

### 2.4 固定仿真相机与平台安装关系

至少定义一个 `camera_0`：

- 输出宽高、帧率、视场角/焦距、快门类型和曝光模型；
- `K`、`D`、`distortion_model`、`R`、`P`；
- `base_link → camera_optical_frame` 的平移、旋转和轴向；
- 图像采样时刻、接收时刻、帧号和时钟来源。

相机内参先使用明确写入配置的**仿真值**，同时保留一个“扰动/错误内参”版本用于鲁棒性实验；不能把分辨率或视场角猜成真实硬件内参。实机到货后必须重新标定并替换该配置。

### 2.5 准备算法和许可环境

按目标可观测性只选一条主线和一条对照：

| 条件 | 主线建议 | 输入 | 备注 |
|---|---|---|---|
| 有 CAD/尺寸、只有单目 RGB | PVNet 或 GDR-Net，必要时用合成数据训练 | RGB、`K/D`、目标模型/关键点 | 需训练/验证划分；输出 6D 位姿，不是类别框 |
| 目标固定且纹理稳定、无 CAD | 固定沙盘建图 + SuperPoint/LightGlue（或 LoFTR）+ 3D-2D PnP | RGB、固定地图、`K/D` | 先验证场景重定位，再截取目标区域；背景误匹配要单独统计 |
| 可提供同步深度和 CAD | FoundationPose 作为扩展候选 | RGB-D、深度内参、目标模型 | 当前硬件边界是单目，不能假设深度可用 |

算法代码、权重、容器/环境、CUDA/PyTorch 版本和许可证写入运行记录。仿真中使用的目标 mesh、纹理和标注不得与测试轨迹泄漏。

## 3. 仿真数据和接口字段设计

接口字段的权威来源是 [`2026-08-25_reference_interface_fields.csv`](2026-08-25_reference_interface_fields.csv) 和代码中的消息/契约；本节只规定仿真如何填充。内部长度统一为 m、角度统一为 rad、时间统一为 ns。

### 3.1 平台 UWB（无人机自身）

给定真值 `p_tag(t)` 和四个 `uwb_anchor_i` 坐标，生成：

```text
r_i(t) = ||p_tag(t) - p_anchor_i|| + bias_i + Gaussian(0, σ_uwb)
```

按场景加入 NLOS 偏置、离群值、丢包、更新率抖动和时间延迟。仿真解算器只接收模拟测距或明确标记为 `uwb` 的平台位置，不能读取真值 `p_base(t)`。记录 `anchor_id`、`range_m`、`range 有效状态`、`原始距离质量标志`、`UWB 定位数据更新率`、`UWB 质量/协方差`、`基站布局版本`、`tag ID` 和 `UWB 标签 → base_link 外参`。

若第一阶段先以平台位姿替代多边测量，必须将其命名为 `synthetic_uwb_platform_pose`，并把多边测量列为下一阶段；不可把无噪声真值直接称为 UWB 精度。

### 3.2 视觉输入与目标观测

渲染器根据 `T_map_base(t)`、`T_base_camera`、`T_map_target(t)` 产生图像。目标的视觉输入不包含标签；渲染真值只进入评估器，不能进入视觉节点。每帧至少保存：

- `frame_sequence`、`sample_timestamp_ns`、`timestamp_clock`、`receive_timestamp_ns`；
- `image_width_px`、`image_height_px`、`encoding/pixel_format`、`payload / 图像字节或外部引用+SHA256`；
- `exposure_start_timestamp_ns/曝光时长`、`gain`、`exposure_us`；
- `camera_frame_id`、`distortion_model`、`K[3x3]`、`D[]`、`R`、`P`；
- `transport`、`packet_loss_or_decode_error`。

图像退化参数应可开关并登记：光照、阴影、曝光、运动模糊、滚动快门近似、压缩、噪声、遮挡、目标纹理变化和背景动态物体。先生成无退化基线，再逐项增加扰动，避免一开始无法判断失败原因。

视觉适配器输出 `/nexus/vision/target_observation`，消息必须复用 `TargetObservation.msg`：`header.frame_id=camera_0`、`target_id` 为机外目标、`source_mode=SOURCE_DIRECT_VISION`、单位 `m`、协方差 36 元素、`confidence` 0～1；无效帧使用 NaN 和 `invalid_reason`，不能复用上一帧。

### 3.3 平台姿态、坐标链和主输出

仿真发布的平台输入可映射到 `/nexus/fcu/odom`，但其语义必须是 `map → base_link`，不能改名为目标位姿。坐标变换按：

```text
T_map_target(t) = T_map_base(t) · T_base_camera · T_camera_target(t)
```

其中 `T_camera_target` 是纯视觉输出，`T_map_base` 是带噪 UWB/平台输入，`T_base_camera` 是配置的安装外参。转换节点输出 `/nexus/vision/map_target_observation`；主链路结果可进入 `/nexus/target/pose`，并保留 `source_mode`、采样时间、接收时间和有效性。

### 3.4 GNSS 的处理

GNSS 字段（如 `GLOBAL_POSITION_INT.lat/lon/alt`、速度和航向）只用于以下两类对照：

1. **室外能力占位**：把 `map` 转成局部 ENU 后注入可控噪声；
2. **室内失效测试**：发布 unavailable、漂移或间歇丢失，验证系统不会把无效 GNSS 当作真值。

室内沙盘实验的主指标不使用 GNSS；不得用虚拟经纬度证明室内定位效果，也不把 GNSS 与 UWB 混成一个未标注的“平台真值”。

### 3.5 本阶段明确不模拟或不作为主输入的字段

`SCALED_IMU.*`、`imu_sample_timestamp_ns`、`angular_velocity_*`、`linear_acceleration_*`、`camera → IMU 外参`、`tag → IMU 外参`、VINS/ORB-SLAM3 惯性模式和 UVINS 不属于本阶段主链路。CSV 中的这些字段可保留为空或标记 `not_used_in_sim_v1`，不能填入零值后伪装成已验证传感器。

## 4. 推荐的实施步骤

### 阶段 0：冻结问题和配置模板

1. 选定一个目标并填写 `target_spec.yaml`：ID、CAD/网格、尺寸、参考点、初始姿态、静态/动态属性和可见性要求。
2. 创建 `map_definition.yaml`、`camera_intrinsics.yaml`、`base_to_camera.yaml`、`uwb_anchor_positions.yaml`、`simulation_noise.yaml`。
3. 为每个 TBD 字段写负责人、获取方法和阻塞条件；未给参数不自行补成实测值。
4. 锁定坐标、单位、时间基准、消息 topic 和算法版本；改变字段、frame、单位或优先级时新增 ADR。

**通过条件**：目标可观测性已判定；配置能在没有实机的情况下生成一条自洽轨迹；所有真值字段与算法输入字段分离。

### 阶段 1：沙盘建模和静态渲染基线

1. 先按相对比例和相对位置建立台面、建筑、道路、植被和目标 mesh；如果尚无实测尺寸，使用 `layout_only` 缩放，并将图 1 仅作为布局参考。
2. 在场景中放置 `map` 原点、四个 UWB 基站、`camera_0` 和目标参考点；导出 TF/模型版本。
3. 固定一个无人机位姿和一个目标位姿，渲染多种距离、俯仰和光照的 RGB 图像。
4. 用渲染器投影目标几何角点，检查图像可见性、遮挡和像素边界。

**通过条件**：目标在至少一个近景、一个中景和一个远景中可见；渲染真值能反投影回图像；模型的相对比例、相对位置和 `z=0` 关系无歧义。若使用 `layout_only`，验收记录必须注明“非绝对尺寸模型”。

### 阶段 2：生成轨迹和三类数据流

1. 设计静止、平移、绕目标环视、升降、偏航和短时失锁轨迹；先用脚本生成，不依赖飞控动力学。
2. 根据轨迹渲染 RGB 帧和目标/平台真值。
3. 根据平台真值生成带噪 UWB 距离或平台位置，包含可控延迟、丢包和 NLOS。
4. 生成 GNSS 正常、漂移、无效三种模式，但在室内主实验中禁用其对目标的贡献。
5. 将图像、平台输入、目标真值、场景版本和随机种子写入同一数据集清单。

**通过条件**：同一随机种子可重生成相同 payload/校验值；算法进程看不到目标真值和无噪平台真值。

### 阶段 3：先做纯视觉相对定位

1. 只给视觉节点 RGB、`CameraInfo` 和目标先验，暂不接 UWB 和 `map`。
2. 按 2.5 节选择 PVNet/GDR-Net 或“固定地图 + 特征匹配 + PnP”主线。
3. 记录目标检测/跟踪可用率、`camera → target_link` 平移误差、旋转误差、重投影误差、置信度和失锁原因。
4. 在无退化基线通过后，逐项加入视角、距离、光照、遮挡、模糊和压缩变化。

**通过条件**：相对位姿输出 frame、单位、时间和有效性符合 `TargetObservation`；失败可由可观测性、匹配、姿态解或输入质量解释。

### 阶段 4：接入平台 UWB 和坐标转换

1. 将带噪平台 UWB 输入发布为 `map → base_link`，先与平台真值独立比较。
2. 加载 `base_link → camera_0` 外参，按采样时间配对平台和图像；显式记录最大允许时间差。
3. 运行坐标变换，输出 `map → target_link`，分别比较视觉相对误差、平台 UWB 误差和端到端误差。
4. 注入时间偏移、UWB 丢包和姿态扰动，验证无效状态、降级和恢复逻辑。

**通过条件**：移动平台时目标世界坐标仍与真值一致；x/y/z 方向、米制单位、姿态方向和时间配对均通过独立检查。

### 阶段 5：形成可复现实验矩阵

最小矩阵如下，具体数值在参数确定后填写，不把目标值当结果：

| 维度 | 至少覆盖 |
|---|---|
| 平台 | 静止、匀速平移、绕目标、升降、偏航 |
| 目标 | 近/中/远距离；台面目标和有高度目标；静止与可控移动 |
| 视觉 | 正常光照、低照/阴影、运动模糊、遮挡、纹理弱化、压缩/丢帧 |
| UWB | 无噪声 sanity、随机噪声、固定偏置、NLOS 离群、延迟、丢包、不同基站布局 |
| GNSS | 禁用（室内主线）、正常占位、漂移、完全无效 |
| 参数 | 正确 `K/D`、焦距扰动、外参扰动、时间偏移 |

训练/调参/测试按轨迹和视角隔离，不能只随机打乱相邻视频帧。每次正式运行采用 `YYYY-MM-DD_E<三位编号>_<slug>`，保留配置、命令、代码提交、权重、随机种子、输入/输出 SHA256 和结论。

### 阶段 6：仿真准入与实机迁移

仿真完成后再整理实机替换清单：

- 用真实 `Image`、`CameraInfo`、采样时间和 `camera_frame_id` 替换渲染器；
- 用现场测量的基站坐标、UWB 标签外参和抓包单位替换合成 UWB；
- 用真实 `base_link → camera` 标定替换仿真外参；
- 用实体沙盘独立测量点建立真实值，不沿用图 1 或仿真模型尺寸；
- 重新运行同一指标脚本，单独建立实机运行编号。

仿真通过只能说明软件链路和算法在合成数据上的行为可复现；不能跳过相机标定、外参、时间同步、UWB 布局和实体真值测量。

## 5. 指标、验收和失败处理

每次运行至少报告以下分项，不只给一个端到端数字：

- **平台 UWB**：`map → base_link` 的位置 RMSE/P95、各轴偏差、姿态误差、可用率；
- **纯视觉**：`camera → target_link` 的平移 RMSE/P95、旋转误差、重投影误差、目标可用率、失锁恢复时间；
- **坐标链**：`map → target_link` 的位置/姿态误差、时间配对误差、端到端延迟；
- **数据质量**：帧率、丢帧/解码错误、UWB 丢包、NLOS 次数、无效消息原因和置信度分布；
- **对照**：GNSS 仅报告是否有效及其误差/漂移，不并入室内主线成绩。

出现以下情况应暂停换算法，先修复数据条件：

1. 目标没有可用 CAD、尺寸、纹理或三维地图；
2. 渲染图像中目标长期不可见、像素过小或被背景遮挡；
3. `K/D`、frame、单位或时间戳不完整；
4. UWB 标签对象、基站编号或距离单位不清楚；
5. 测试轨迹与训练轨迹泄漏，导致结果无法解释。

仿真中的精度只写成“合成场景结果”，并注明模型、渲染器、噪声和真值生成方式；不得写成实体沙盘或实机精度。
