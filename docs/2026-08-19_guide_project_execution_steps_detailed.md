## 使用方法

本文不是把任务拆成“谁写哪个函数”，而是为每一步回答六个问题：

1. 这一步要解决什么问题；
2. 开始前需要哪些输入；
3. 团队应该按什么顺序推进；
4. 哪些方案可以直接借用，哪些必须自己定义；
5. 形成什么文档、数据或决定；
6. 什么条件满足后才能进入下一步。

每一步都有“停止条件”。如果停止条件未满足，应停在当前步骤并记录原因，不要用后续步骤的结果掩盖前置问题。

## 总体依赖关系

```text
目标与验收边界
        ↓
接口/坐标/数据契约
        ↓
硬件前软件骨架 ──────┐
        ↓             │
硬件验收与安装        │
        ↓             │
单传感器和信息通道 ────┘
        ↓
世界坐标与标定
        ↓
单源基线实验 E001
        ↓
融合与降级
        ↓
动态/遮挡实验 E002/E003
        ↓
可视化、演示、答辩和交付
```

这里的“算法”分为两层：

- 前置算法骨架：没有真实硬件也可以准备，用于验证消息、坐标和统计口径；
- 正式算法选型：必须依赖真实 UWB/视觉基线数据，不能在数据出来前拍脑袋决定。

## 步骤 1：明确定位对象与验收边界

### 目标

把“定位对象”从“无人机系统”进一步具体化为一个可测量的外部目标，并规定最后要用什么证据判断定位是否有效。

### 开始前准备

- 阅读 ADR-002，确认无人机是传感器、通信和计算平台；
- 列出实际可定位的目标候选：目标模型、移动物、标记板或其他外部物体；
- 盘点沙盘允许的活动空间、目标尺寸、目标高度和安全限制；
- 明确最终是展示静态目标、动态目标，还是两者都展示。

### 指导顺序

1. 给目标定义唯一名称和物理参考点，例如几何中心或底部中心；
2. 决定目标是否能安装 UWB 标签、视觉标签或两者；
3. 在“目标直接测量”和“平台间接测量”中选择一个首版模型；
4. 为静态、动态和异常场景分别写验收问题；
5. 把精度目标改写成“待验证指标”，不得作为既定结论；
6. 明确演示必须证明什么，哪些内容只是后续扩展。

### 可以直接借用的模块

- ADR-002 的目标边界和两种测量模型；
- 模块图中“目标世界坐标”作为 ROS2 主输出的定位；
- 官方飞控状态只能作为平台状态来源，不能直接替代目标位置。

### 必须自己定义的内容

- 目标物理形态和 `target_link` 参考点；
- 标签安装方式；
- 目标是否允许人工固定在验证点；
- 核心区、过渡区和 UWB 兜底区的具体范围；
- 每一类演示的成功判据。

### 产出

- 《目标与验收边界说明》；
- 测量模型决策记录；
- 目标照片和 `target_link` 参考点说明；
- 初版指标表和场景清单。

### 通过条件

团队能够用一句话回答：

> 我们定位的是哪个外部目标，输出的是它在什么坐标系下的位置，在哪些场景下用什么真值判断好坏？

如果仍然把 `base_link`、无人机位置和目标位置混用，不进入步骤 2。

## 步骤 2：冻结接口、坐标、单位和记录格式

### 目标

让 ROS1、ROS2、离线评估和网页展示对同一条数据有完全一致的理解。

### 开始前准备

- 列出所有可能的数据来源：官方 UWB、飞控 odometry、视觉检测、相机信息、真值和实验元数据；
- 区分采样时间、接收时间和显示时间；
- 确定 `map`、`camera_i`、`base_link`、`target_link`、`uwb_anchor_i` 等 frame 的职责；
- 阅读 `docs/architecture/interfaces.md` 和 `coordinate-frames.md` 的现有草案。

### 指导顺序

1. 先写每个消息的“语义”，再写话题名称；
2. 区分平台状态、目标观测和目标世界坐标三类消息；
3. 固定所有长度使用米、时间使用纳秒或统一 ROS 时间语义；
4. 固定 NED/ENU、右手系、轴向和四元数约定；
5. 规定缺失、过期、frame 不一致、单位不明和目标 ID 不一致时的处理；
6. 规定消息版本、序号和配置版本如何登记；
7. 最后再决定使用标准 bridge、专用 bridge 还是轻量网络通道。

### 可以直接借用的模块

- `nexus_msgs` 的目标观测字段设计；
- ROS1 官方 `fcu_core` 作为硬件兼容层；
- 模块图中“ROS1 官方飞控桥接 → ROS2 算法层”的分层；
- `rosbridge` 作为浏览器数据传输参考，但不让网页承担坐标转换或指标计算。

### 必须自己定义的内容

- UWB 消息到底代表无人机还是外部目标；
- 目标直接测量或平台间接测量的字段映射；
- bridge 的部署位置、频率和实际网络条件；
- 过期阈值、配对阈值和异常状态命名；
- 网页中如何显示“无观测”，避免把零值当作有效位置。

### 产出

- 接口表；
- frame/单位/时间约定；
- 消息字段字典；
- 通道契约说明；
- 错误和无效状态表。

### 通过条件

拿一条模拟消息，任何成员都能判断它是平台状态还是目标位置，知道它在哪个 frame、单位是什么、何时过期，以及能否参与融合。

## 步骤 3：硬件到货前完成最小软件骨架

### 目标

在没有真实传感器数据时，先验证项目边界、数据结构、坐标逻辑和评估口径，而不是伪造精度结果。

### 开始前准备

- 步骤 1 的目标语义和步骤 2 的接口契约；
- ROS2 Humble 环境；
- 固定几何样例和人工构造的观测数据；
- 计划中的包边界和模块责任表。

### 指导顺序

1. 先划分消息、视觉、坐标、融合、启动和展示职责；
2. 为每个模块写输入、输出、无效行为和验证方法；
3. 先支持单源目标观测，再支持双源融合；
4. 先支持离线回放，再考虑实时输入；
5. 先实现统一指标定义，再制作图表；
6. 为每个固定样例标注“测试样例”，与未来实测数据隔离。

### 可以直接借用的模块

- AprilTag 检测和 OpenCV ArUco 作为视觉适配候选；
- `caliscope` 作为多相机标定/三角测量的条件性参考；
- ROS2 `tf2` 作为坐标变换框架；
- 模块图中列出的官方 `fcu_core`、FanciSwarm 和 rosbridge 作为外部依赖边界；
- Kalman/贝叶斯资料仅作为理解和后续研究参考，不作为首版必需模块。

### 必须自己定义的内容

- 目标消息如何保留来源模式和协方差；
- 目标直接测量与平台间接测量的两个独立入口；
- 评估工具的输入字段和统计口径；
- 模拟数据与实测数据的目录边界；
- 哪些模块属于“可选扩展”，不阻塞主线。

### 产出

- 软件包边界图；
- 消息和数据字典；
- 模拟回放场景；
- 评估指标定义；
- 硬件到货后的接入清单。

### 通过条件

没有真实硬件时，仍可验证一条“观测 → 坐标变换 → 单源输出 → 融合 → 指标”的逻辑链；但输出必须明确标记为测试样例。

## 步骤 4：硬件验收、组装与安全检查

### 目标

确认硬件型号、供电、通信、重量、安装和视场都满足实验条件，避免定位问题其实是机械或电气问题。

### 开始前准备

- 官方硬件资料和连接方式；
- 硬件清单和安装位置草图；
- 供电、电流、散热和急停信息；
- 目标和无人机的标签安装方案候选。

### 指导顺序

1. 逐项核对 Mcontroller V7、FanciSwarm、DWM1000 标签、相机和伴随计算机；
2. 区分“到货验收”与“功能验收”，先记录外观和型号，再通电；
3. 空载、低风险、非飞行状态下确认通信；
4. 测量相机、标签、树莓派和线缆的质量与安装位置；
5. 检查重心、螺旋桨、视场、散热和线缆松脱风险；
6. 固定设备后拍照、编号和复测；
7. 明确哪些操作需要断电、锁桨或人工监护。

### 可以直接借用的模块

- 官方 FanciSwarm 四基站 + DWM1000 作为 UWB 硬件基线；
- 官方 `fcu_core` 作为 ROS1 通信基线；
- 树莓派 5 作为轻量 ROS1/记录端，外部主机作为视觉和分析端；
- 官方视觉套件和 D435/RGB 只能在实际购买和接口确认后采用。

### 必须自己定义的内容

- 标签装在目标还是无人机；
- 相机装在无人机、固定三脚架还是两者组合；
- 线缆、支架和电池的安装方式；
- 桌面测试、锁桨测试和低风险飞行测试的顺序；
- 设备移动后的重新标定责任。

### 产出

- 硬件验收表；
- 接线图和安装照片；
- 载荷质量/重心记录；
- 风险、急停和操作人清单；
- 硬件版本登记。

### 通过条件

硬件能稳定上电和通信，安装后不影响安全，且团队已经知道 UWB 和视觉究竟在观测哪个对象。任何供电、结构、散热或标签语义问题未解决时，不进入精度实验。

## 步骤 5：分别打通 UWB、视觉和 ROS1/ROS2 通道

### 目标

先证明每个单独模块是可用的，再把它们连接起来。这样出现误差时能判断是传感器、通道还是坐标变换造成的。

### 开始前准备

- 已通过硬件验收；
- 目标/平台测量模型已经选定；
- 录制格式和时间字段已经冻结；
- 每个模块有单独的验收表。

### UWB/飞控部分指导

1. 按厂商建议布置四基站，记录位置、高度、配置和环境；
2. 用 App、官方链路和 SD 日志确认位置输出是否稳定；
3. 明确输出的标签对象和坐标语义；
4. 记录静止时的均值、波动、丢包和延迟；
5. 只有厂商开放原始测距时，才考虑模块图中提到的 LS/鲁棒 LS 等离线参考；
6. 没有原始测距时，不做 Chan/Taylor/TDOA 的伪比较。

### 视觉部分指导

1. 确认相机是否能输出原始图像、内参、帧率和时间戳；
2. 先判断单相机是否足以覆盖核心区；
3. 再判断是否值得接入多相机；
4. 先使用 AprilTag/ArUco 获得稳定检测，再评估 PnP、双目或多相机三角测量；
5. 记录检测成功率、遮挡情况、重投影误差和图像延迟；
6. 视觉失效时必须输出无观测，而不是沿用上一帧伪装成正常输出。

### ROS1/ROS2 通道部分指导

1. 先传平台状态和原始观测，再传融合输出；
2. 核对单位、轴向、采样时间、接收时间、序号和目标 ID；
3. 观察桥接延迟、丢包、乱序和重连行为；
4. 保留 ROS1 原始记录和 ROS2 转换后记录，便于定位问题；
5. ROS2→ROS1 回传仅在演示需要控制或跟踪时增加。

### 产出

- UWB 单独记录；
- 视觉单独记录；
- 通道映射和延迟报告；
- “平台状态/目标观测/目标输出”语义核对表。

### 通过条件

每个模块都能独立录制和回放；任何一条数据都能回答“谁产生、何时采样、在哪个坐标系、代表哪个对象”。

## 步骤 6：建立世界坐标系并完成标定

### 目标

让 UWB、视觉、无人机机体和外部目标真正落在同一个物理世界中。

### 开始前准备

- 实体沙盘和固定基准点；
- 可重复测量的工具和方法；
- 相机标定板或 AprilGrid；
- UWB 基站实际安装坐标；
- 标定点和独立验证点清单。

### 指导顺序

1. 在沙盘上建立 `P0/P1/P2`，定义 `map` 原点、x、y、z；
2. 测量基站、相机、目标标签和验证点；
3. 完成相机内参，再求相机到 `map` 的外参；
4. 配置或拟合 UWB 到 `map` 的变换；
5. 测量标签中心与 `target_link` 的安装偏移；
6. 用独立验证点检查方向、单位、重投影和空间误差；
7. 将标定结果与日期、版本、点位和运行编号绑定。

### 可以直接借用的模块

- `caliscope` 作为多相机标定参考；
- OpenCV/PnP 和 AprilTag/ArUco 作为单相机标定参考；
- ROS2 `tf2` 作为运行时坐标树；
- 模块图明确列出的“坐标标定 + tf2 统一变换”作为必须自写的项目模块。

### 必须自己定义的内容

- 沙盘的原点、轴向和基准点；
- 基站天线参考点和相机光心的测量方法；
- 目标参考点与视觉/UWB 标签的外参；
- 标定点/验证点划分；
- 标定后设备移动的复测规则。

### 产出

- `map` 定义；
- 沙盘点位和测量记录；
- 相机内外参；
- UWB 基站或 UWB 坐标变换；
- 目标标签外参；
- tf2 树和独立验证报告。

### 通过条件

验证点上的误差、轴向、单位和变换方向都可解释；若变换只能通过“手动平移到看起来重合”实现，不能进入步骤 7。

## 步骤 7：先做单源静态基线，再比较算法

### 目标

回答“UWB 单独有多准、视觉单独有多准、它们在哪里失效”，为后续融合提供真实依据。

### 开始前准备

- 步骤 6 已冻结的标定文件；
- E001 的点位、轮次、停留时间和公共时间栅格；
- 真值测量记录；
- 代码、配置和设备版本登记方式。

### 指导顺序

1. 冻结算法和配置，不针对单个点位临时调参；
2. 同时录制传感器原始数据和接收数据；
3. 先分析官方 UWB 基线；
4. 再分析单相机视觉；
5. 有条件时再分析多相机；
6. 用同一真值、同一时间栅格和同一统计口径比较；
7. 分别报告精度、可用率、频率、延迟和异常数量；
8. 将“不适用”和“不可用”与“精度差”区分开。

### 可以直接借用的模块

- E001 已定义的 8 点×3 轮×60 s 计划；
- 模块图中官方 UWB 基线、AprilTag/ArUco 视觉基线；
- 现有离线评估工具的指标口径。

### 必须自己定义的内容

- 最终测试点具体位置；
- 目标静止治具和真值复核方式；
- 视觉主相机和标签字典/尺寸；
- 哪些算法在当前硬件接口下确实适用；
- 何时判定某方案“不适合进入融合”。

### 产出

- E001 运行目录；
- 单源指标表；
- 点位误差图和失败样本；
- 算法选型决策记录。

### 通过条件

所有比较均使用同一时间和真值口径；没有任何测试样例、规划目标或厂商宣传值被当作本项目实测结果。

## 步骤 8：实现融合与降级策略

### 目标

在单源结果已经可信的前提下，让视觉和 UWB 互相补充，并明确传感器失效时系统怎么表现。

### 开始前准备

- E001 的单源误差、可用率和延迟；
- 各观测的协方差或质量指标；
- 观测过期和时间配对规则；
- 视觉丢失、UWB 异常和两者同时无效的场景定义。

### 指导顺序

1. 先确定哪些观测能进入融合；
2. 先采用固定协方差或固定质量分级，建立可解释基线；
3. 统计视觉可见、视觉不可见、UWB 正常和 UWB 异常时的来源组合；
4. 再根据实测残差决定是否需要自适应权重；
5. 只在确有必要时研究 Kalman/UKF 或图优化；
6. 为每种失效情形定义输出状态、报警和恢复方式；
7. 比较融合前后的相同时间样本，而不是比较不同样本集。

### 可以直接借用的模块

- 模块图中的轻量 Kalman 资料作为学习参考；
- 飞控已有 EKF 作为飞行平台内部能力，不在 ROS2 重写飞控闭环；
- rosbridge/ros2 bag 作为融合状态展示和回放的数据出口。

### 必须自己定义的内容

- 多相机基于视角、距离、检测置信度的权重；
- UWB 与视觉的质量门限；
- 目标观测来源模式；
- 降级状态的切换和恢复条件；
- 融合改进的统计判据。

### 产出

- 融合方案说明；
- 参数冻结记录；
- 来源模式和降级状态表；
- 融合与最佳单源对比报告。

### 通过条件

融合没有降低可用率，且在预先规定的区域和指标上有真实改进；否则保留最佳单源作为主方案，不为了“有融合”而强行使用融合输出。

## 步骤 9：完成动态、遮挡和异常验证

### 目标

确认系统不只在静态、无遮挡、精心摆放的点位上有效。

### 开始前准备

- E001 已完成并保留其配置；
- 动态轨迹和速度范围；
- 遮挡、NLOS 或可控多径的安全方案；
- 运动过程中的真值或参考轨迹方法；
- 失败记录规则。

### 指导顺序

1. 先做低速、短距离、可重复的直线运动；
2. 再做圆形或“8”字轨迹；
3. 记录速度、加速度、转弯和目标朝向；
4. 单独制造视觉遮挡并记录失效开始、持续和恢复时间；
5. 单独测试 UWB 异常或 NLOS，不把所有干扰一次叠加；
6. 最后测试多故障组合；
7. 保留失败片段，不只挑成功片段制作图表。

### 可以直接借用的模块

- E001 的指标和数据记录规范；
- 模块图中的状态切换、观测质量和异常处理方向；
- Dashboard 的事件流和运行编号显示设计。

### 必须自己定义的内容

- 动态真值获取方式；
- 最大安全速度和活动范围；
- 遮挡物、遮挡时间和恢复条件；
- NLOS/多径测试的可控程度；
- 动态系统的通过标准。

### 产出

- E002 动态运行；
- E003 遮挡/NLOS 运行；
- 失效和恢复时间统计；
- 动态轨迹图和失败案例。

### 通过条件

静态、动态和异常结论相互独立；不得用 E001 的静态结果替代动态或遮挡验证。

## 步骤 10：打通端到端应用和可视化

### 目标

把数据采集、坐标转换、算法输出、评估和展示串成可重复的完整流程。

### 开始前准备

- 已冻结的消息、坐标和来源模式；
- 至少一份可回放实验数据；
- Dashboard 信息架构；
- 在线和离线两种演示场景。

### 指导顺序

1. 先设计观众需要看到的最少信息：目标在哪里、来源是什么、数据是否新鲜、误差如何；
2. 再安排 RViz2 的坐标轴、目标、平台和验证点图层；
3. 再设计 Dashboard 的主视图、状态栏、误差视图和标定辅助视图；
4. 规定在线数据和回放数据必须共享同一消息语义；
5. 将标定、调参和真值坐标设为受控配置，不能由网页临时修改；
6. 为无数据、过期、断桥和来源切换设计明确状态。

### 可以直接借用的模块

- 模块图中的 ROS2 RViz2；
- `rosbridge_suite` 或 `ros2 bag` 作为浏览器数据出口；
- 现有 Dashboard 信息架构中关于主地图、状态卡片、事件和标定视图的设计。

### 必须自己定义的内容

- 目标与平台的视觉层级；
- 来源模式和误差图的表达方式；
- 在线/回放切换方式；
- 演示时要显示的验证点和真值；
- 失效状态和告警文案。

### 产出

- 端到端流程图；
- RViz2 和 Dashboard 信息设计；
- 在线/回放演示说明；
- 数据状态和告警字典。

### 通过条件

新成员仅阅读说明即可复现一次在线或回放演示，并能分清平台位置、目标位置、原始观测和融合结果。

## 步骤 11：固化演示脚本和答辩证据

### 目标

把技术链路转化为评委能看懂、团队能复现、数据能追溯的演示故事。

### 开始前准备

- 已完成的 E001/E002/E003 运行；
- 通过验证的指标表和图表；
- 可回放数据和演示硬件；
- 评委可能提出的问题清单。

### 指导顺序

1. 选择一个主故事，不在现场展示所有内部模块；
2. 先展示目标和世界坐标，再展示 UWB 基线；
3. 视觉可见时展示修正效果；
4. 遮挡时展示降级和来源切换；
5. 恢复后展示重新获得观测；
6. 每个数字同时标注运行编号、样本数、场景和单位；
7. 准备在线失败时的纯回放版本；
8. 预演“为什么这样选、精度如何测、失败怎么办”三个问题。

### 可以直接借用的模块

- Dashboard 主视图和标定/证据辅助视图；
- 模块图中的目标世界坐标、RViz2、rosbridge 和误差统计模块；
- E001/E002/E003 的实验证据格式。

### 必须自己定义的内容

- 演示目标、路线和停留点；
- 现场讲解顺序；
- 主视频和备份视频；
- 硬件故障、网络中断、视觉丢失时的 Plan B；
- PPT 中“目标值/实测值/未验证”的视觉区分。

### 产出

- 演示脚本；
- 主视频与回放视频；
- PPT 图表；
- Q&A 资料；
- 证据索引更新。

### 通过条件

演示可以在没有临时调参的情况下重复完成；所有展示数字都能回到一个正式运行目录。

## 步骤 12：最终审查与交付

### 目标

确认项目交付的是可解释、可复查的系统证据，而不是一组无法重现的截图和口头结论。

### 开始前准备

- 代码、配置、实验、输出和答辩目录；
- 版本、依赖和环境登记；
- 每项结论的来源运行编号；
- 未完成事项清单。

### 指导顺序

1. 按“已实现、已测量、规划目标、未验证”重新检查报告措辞；
2. 检查所有图表的单位、样本数、异常规则和坐标系；
3. 检查每个实验是否能找到配置、代码版本和原始数据位置；
4. 检查 ROS1/ROS2/bridge 的消息和时间坐标映射；
5. 检查是否误把无人机位置写成目标位置；
6. 检查 Dashboard、PPT 和视频是否展示了不存在的精度；
7. 将未验证项目单独列为后续工作；
8. 形成最终交付清单和版本标签。

### 可以直接借用的模块

- 仓库 `AGENTS.md` 的证据和 Git 规则；
- `experiments/README.md` 的运行目录和命名规则；
- 模块图中“自己写”的坐标、融合、评估和总装模块清单，作为自研工作核对表。

### 必须自己定义的内容

- 最终演示主方案；
- 哪些算法列为主方案、备选方案和未完成方案；
- 版本冻结时间；
- 交付包中包含哪些视频、图表和报告；
- 后续事项的优先级。

### 产出

- 证据索引；
- 交付清单；
- 未验证项清单；
- 最终版本记录；
- 项目复盘记录。

### 通过条件

任何关键结论都能由“代码版本 + 配置 + 数据 + 运行记录 + 统计口径”复核。不能复核的内容只能作为猜测或后续计划，不能写成项目成果。

## 模块图中的“直接借用”和“必须自研”总表

### 优先直接借用或适配

| 能力 | 模块图中的候选 | 使用边界 |
|---|---|---|
| 飞控/UWB 硬件兼容 | FanciSwarm、Mcontroller V7、官方 `fcu_core` | 先验证官方输出，不默认解释为目标位置 |
| 单目标视觉检测 | AprilTag、OpenCV ArUco | 先做单路，接口和标签尺寸以实际硬件为准 |
| 多相机标定/三角测量 | `caliscope` | 只有多路原始图像、时间戳和内参都可用时启用 |
| ROS2 坐标树 | `tf2` | 变换定义和实测外参必须由项目维护 |
| 浏览器数据出口 | rosbridge/ros2 bag | 浏览器只展示，不负责定位和评估 |
| 飞控内部估计 | Mcontroller 内置 EKF | 不在 ROS2 重写飞控安全闭环 |

### 必须由项目自己定义或编写

| 能力 | 原因 |
|---|---|
| 目标语义和 `target_link` | 开源模块不知道项目实际目标是什么 |
| 沙盘 `map` 建立与物理标定 | 必须使用现场真实测量 |
| UWB/视觉/平台坐标统一 | 与具体安装位置和标签偏移有关 |
| UWB 基站 GDOP 布局判断 | 需要结合实体沙盘和实际基站位置 |
| 多相机置信度加权 | 需要结合视角、距离、检测质量 |
| 自适应融合和降级切换 | 必须根据 E001/E002/E003 实测证据决定 |
| 误差统计和证据图表 | 指标口径必须服从本项目实验协议 |
| 端到端 bringup 和演示编排 | 需要适配两套 ROS 和真实设备 |
| Dashboard 前端信息表达 | rosbridge 只解决数据传输，不解决展示语义 |

## 项目推进时的决策顺序

当团队对方案产生分歧时，按以下顺序决策：

1. 先问是否影响目标语义、坐标、单位和真值；
2. 再问是否有真实硬件接口和数据支持；
3. 再问是否能通过独立实验验证；
4. 最后才比较算法复杂度、展示效果和扩展性。

只要前一层没有证据，后一层就不应成为阻塞项目主线的理由。
