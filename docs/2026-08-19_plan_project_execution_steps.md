# NEXUS 项目完整执行步骤

- 日期：2026-08-19
- 类型：实施计划
- 状态：draft
- 适用范围：从当前准备阶段到最终答辩演示的主线执行顺序
- 事实来源：`docs/PROJECT_INDEX.md`、`docs/无人机高精度目标定位项目规划 (2).md`、`docs/decisions/2026-08-18_ADR-002_target-localization-scope.md`
- 详细指导：`docs/2026-08-19_guide_project_execution_steps_detailed.md`

## 先说结论：项目不应从“先做算法”或“先装硬件”开始

正确顺序是：

```text
1. 明确定位对象和验收口径
2. 冻结接口、坐标、单位和数据记录格式
3. 硬件到货前完成软件骨架和离线工具
4. 硬件验收、组装和单机安全检查
5. 分别打通 UWB、视觉和 ROS1/ROS2 通道
6. 建立坐标系并完成标定、时间检查
7. 先做单源静态基线，再比较算法
8. 实现融合和降级策略
9. 做静态、动态、遮挡/异常三类验证
10. 固化演示方案、数据证据和答辩材料
```

“算法”会在第 3 步先做可运行的最小版本，但真正的算法选型要等第 7 步的实测数据；“通道”要在第 2 步先定义契约，第 5 步再接真实设备；“硬件组装”放在软件接口可检查之后，避免装好以后才发现消息语义、供电或坐标系不匹配。

| 2 | 把数据如何流动写成契约 | 接口表、坐标/单位约定、版本规则 | ROS1、ROS2、离线工具使用同一语义 |
| 3 | 在无硬件时做出可测试的软件骨架 | ROS2 包、消息、离线评估工具 | 能用固定样例编译、测试、回放 |
| 4 | 确认硬件能安全工作且安装方案成立 | 硬件清单、接线图、装配记录 | 通电、通信、重量、重心和急停检查通过 |
| 5 | 分别取得每个传感器的原始/官方输出 | UWB 基线、视觉基线、飞控状态记录 | 每路数据都有时间戳、单位、frame 和来源 |

## 1. 明确定位对象与验收边界

**简要总结：** 先定义“被定位的外部目标”，再定义精度、场景和验收方式。

**详细解释：**

- 无人机是传感器、通信和计算平台；被定位对象是无人机之外的目标。无人机自身状态使用 `base_link`，目标使用独立的 `target_link` 和 `target_id`。
- 硬件到货前保留两种测量模型：
  - 目标直接测量：目标同时携带 UWB 标签和视觉标记；
  - 平台间接测量：UWB 测无人机，视觉测目标相对位置，再通过外参计算目标世界坐标。
- 到货后必须通过一条决策记录选定其中一种，不能把两种模型的数据混在同一实验里。
- 先写验收口径：静态核心区、全场兜底、动态和遮挡分别报告哪些指标。5 cm 是冲刺目标，未经运行数据验证不能写成结果。

**产出：** 范围说明、测量模型决策、验收指标表、目标物理参考点照片。

**通过条件：** 任何成员都能回答“定位谁、输出在哪个坐标系、用什么真值判断好坏”。

## 2. 冻结接口、坐标、单位和记录格式

**简要总结：** 先建立“通道契约”，再写真实 bridge；先规定字段含义，再决定采用哪种传输实现。

**详细解释：**

- ROS1 Noetic + 官方 `fcu_core` 只负责硬件兼容；ROS2 Humble 负责视觉、坐标转换、目标定位、融合、评估和展示。
- 固定目标输出语义：`/nexus/target/pose`；每条消息至少包含采样时间、接收时间、`frame_id`、`target_id`、来源模式、米制位置、协方差和置信度。
- 固定平台状态入口，如 `/nexus/fcu/odom` 和 `/nexus/fcu/imu`，但不把平台位姿直接改名成目标位姿。
- 写清 NED/ENU、右手系、米/厘米、采样时间/接收时间、过期阈值和版本号。
- 传输方式（`ros1_bridge`、专用 bridge 或轻量网络通道）可以后定，但消息 envelope 和映射规则不能后定。

**产出：** `interfaces.md` 更新、消息定义、通道契约测试、坐标约定草案。

**通过条件：** 用模拟消息即可检查字段完整性、序号连续性、单位和 frame 错误拒绝。

## 3. 硬件到货前完成最小软件骨架

**简要总结：** 先做能编译、能测试、能离线回放的“细骨架”，不要在没有数据时假装完成精度算法。

**详细解释：**

- ROS2 建立 `nexus_msgs`、`nexus_vision_localization`、`nexus_coord_transform`、`nexus_fusion_localization`、`nexus_bringup` 和可视化包。
- 先实现最小链路：模拟观测 → 坐标转换 → 单源输出 → 固定协方差加权 → 指标计算。
- 视觉节点先支持图像/相机参数接口和 AprilTag/ArUco PnP；不把相机型号、标签尺寸和真实外参写死。
- 离线工具先支持 CSV/JSON，计算 RMSE、P50/P95、最大误差、可用率、频率和延迟。
- 使用固定几何样例测试公式；样例不能进入 `experiments/runs/`、`outputs/` 或 `defense/` 冒充实测。

**产出：** ROS2 工作空间、单元测试、离线评估 CLI、模拟数据回放脚本。

**通过条件：** `colcon build`、`colcon test` 和所有工具 `--help` 通过；没有真实硬件数据也能验证接口和公式。

## 4. 硬件验收、组装与安全检查

**简要总结：** 硬件先“验收和测量”，再“固定和接线”，最后才允许运行定位实验。

**详细解释：**

1. 登记 Mcontroller V7、FanciSwarm UWB 四基站、机载标签、相机、伴随计算机、电池、线缆和安装件的型号、版本和序列号（敏感信息只做内部登记）。
2. 按官方资料确认供电、电平、USB/串口或网络连接方式；先空载通电，不挂载全部设备。
3. 测量每个载荷的质量、安装位置和重心变化，确认不会影响飞行安全；固定标签和相机后再次检查螺旋桨、视场和散热。
4. 画出接线图和安装照片，标注 UWB 标签到底装在目标上还是无人机上。
5. 先做桌面通信测试，再做电机不转的传感器测试，最后才做低风险悬停或静态目标测试。

**产出：** 硬件清单、接线图、安装尺寸/重量记录、上电检查表、风险与急停方案。

**通过条件：** 无掉电、无异常发热、消息能读到、载荷不松动；任何供电或机械问题未解决前不得进入飞行实验。

## 5. 分别打通 UWB、视觉和 ROS1/ROS2 通道

**简要总结：** 一次只接通一条链路，先证明“它单独能工作”，再把链路合并。

**详细解释：**

### 5.1 UWB/飞控链路

- 按厂商要求部署四基站，记录实际三维坐标、安装高度、通道和配置版本。
- 确认官方输出对应哪个标签对象；若只输出无人机位置，必须标为平台状态，不得写成目标 UWB 位置。
- 记录官方位置、飞控时间、ROS 接收时间和丢包情况；不先假定厂商标称精度就是本项目结果。

### 5.2 视觉链路

- 确认输入是机载相机、外部固定相机还是多相机；确认原始图像、分辨率、帧率、快门和时间戳。
- 先完成单相机检测和 PnP，再决定是否增加双目/多相机三角测量。
- 记录检测成功率、重投影误差和图像延迟；视觉不可用时输出明确的“无观测”。

### 5.3 ROS1→ROS2 通道

- ROS1 适配层读取官方 topic，负责单位、轴向、时间和字段映射；ROS2 不解析 MAVLink、串口或厂商私有协议。
- 先传平台状态和观测 envelope，再传融合结果；逐项测试序号、时间戳、frame、单位和过期规则。
- ROS2→ROS1 回传不是首版必需项，只有演示确实需要控制/跟踪时才增加。

**产出：** UWB 记录、视觉记录、bridge 映射表、通道延迟/丢包报告。

**通过条件：** 每一路单独录包并能离线回放；缺失、过期或 frame 错误不会被静默补写。

## 6. 建立世界坐标系并完成标定

**简要总结：** 算法前先把“所有数据是不是在同一个地方”证明清楚。

**详细解释：**

- 定义 `map` 原点、轴向、单位和目标参考点；测量 UWB 基站、相机、目标标记和无人机安装外参。
- 完成相机内参/畸变标定，再完成各相机到 `map` 的外参标定；标定数据与评估数据分开。
- 将 UWB 坐标系、相机坐标系、机体坐标系和目标坐标系通过冻结的刚体变换连接到 `map`。
- 用已知点做独立复核：点位不参与重新拟合，只用于检查平移、旋转、轴向和单位是否正确。
- 同时测量采样时间到接收时间的延迟；先量出误差，再决定是否需要更复杂的同步机制。

**产出：** 标定文件、`tf2` 树截图/检查结果、坐标与时间验证记录。

**通过条件：** 已知点转换方向正确、单位一致、外参版本冻结；否则停止后续精度实验。

## 7. 先做单源静态基线，再比较算法

**简要总结：** 不要先调融合参数；先知道 UWB 和视觉各自的真实表现。

**详细解释：**

- 以 E001 为第一项正式实验：至少 8 个真值点（核心区 3、过渡区 3、UWB 区 2），每点 3 轮，每轮稳定 10 s 后评估 60 s。
- 在同一公共时间栅格比较：官方 UWB、单相机 PnP、多相机三角测量（未部署则标记不适用）。
- 统计 3D RMSE、P50/P95、最大误差、轴向偏差、可用率、更新频率、延迟和视觉重投影误差。
- 不能用另一个算法补齐缺失样本；不可用样本计入可用率损失。
- 若官方接口不开放原始测距，不再虚构 Chan/Taylor/TDOA 对比；比较实际可获得的官方输出、视觉和融合链路。

**产出：** `experiments/runs/YYYY-MM-DD_E001_static_target_localization_baseline/`、算法对比表、误差图。

**通过条件：** 真值、配置、代码版本和原始数据均可追溯；E001 未完成前不宣称达到任何精度目标。

## 8. 实现融合与降级策略

**简要总结：** 只融合“已经证明语义正确、坐标一致、时间有效”的观测。

**详细解释：**

- 第一版采用固定协方差加权，先验证融合是否比同一时间点的最佳单源更好；没有证据前不直接上复杂 EKF/UKF/图优化。
- 观测必须满足：目标 ID 一致、frame 一致、时间差在阈值内、未过期、协方差有效。
- 视觉可见时使用视觉修正；视觉丢失时保留 UWB 基线；两者都无效时输出无效状态并报警，不伪造位置。
- 记录每次输出的来源模式（UWB、视觉、融合）和配对延迟，便于解释误差变化。
- 融合只有在核心区误差确实下降且可用率不下降时，才能写成“带来改进”。

**产出：** 融合节点、参数文件、来源模式统计、降级测试记录。

**通过条件：** 单源、双源、过期和无观测场景均可回放；输出不会把平台位姿误标为目标位姿。

## 9. 做三类正式验证实验

**简要总结：** 静态回答“准不准”，动态回答“跟不跟得上”，遮挡/异常回答“坏了会怎样”。

**详细解释：**

1. **E001 静态基线：** 正常视线、目标静止、冻结配置，完成单源和固定协方差融合比较。
2. **E002 动态轨迹：** 设计直线、圆形或“8”字轨迹，报告轨迹误差、延迟、频率和丢帧；动态数据不能回填 E001。
3. **E003 遮挡/NLOS/异常：** 人为遮挡视觉、改变 UWB 视线或制造可控多径，验证降级、恢复时间和报警；记录失败，不只保留成功片段。

每个实验都要新建运行目录，登记环境、命令、数据位置、代码提交、配置 SHA256、真值方法和未验证项。原始视频、rosbag 和编译产物放外部位置并登记校验值。

**产出：** E002/E003 运行记录、分场景指标、失败案例和结论边界。

**通过条件：** 每个结论都能指向具体运行编号；静态、动态和异常场景不混淆。

## 10. 打通端到端应用和可视化

**简要总结：** 把“采集—计算—坐标—评估—展示”变成一条可重复的启动和回放流程。

**详细解释：**

- `nexus_bringup` 提供参数加载、topic remap、tf2 配置和录包入口。
- RViz2 同时显示 `map`、平台、目标观测、融合目标和真值/测试点；图例必须区分来源模式。
- Dashboard 显示目标坐标、置信度、当前来源、延迟、误差曲线和数据状态；没有观测时显示“无数据”，不显示 0。
- 准备在线和离线两条演示路径：硬件在线失败时，用已登记运行包回放，保证演示仍可解释。

**产出：** 一键启动脚本、录包/回放脚本、RViz2 配置、Dashboard 页面。

**通过条件：** 新成员按 README 可以启动；在线和回放显示的字段语义一致。

## 11. 固化演示脚本和答辩证据

**简要总结：** 演示不是临时飞一遍，而是用已验证数据讲清楚系统价值。

**详细解释：**

- 设计一个短主线：目标进入场景 → UWB 给出绝对基线 → 视觉可见时精修 → 遮挡时降级 → 恢复后重新融合。
- 选择 3～4 个有明确真值的沙盘点位，展示坐标、误差和来源模式，不只展示漂亮轨迹。
- 视频和 PPT 中每个数字都标注实验编号、场景、样本数和单位；5 cm 只有在对应运行的 P95、可用率和真值不确定度满足条件时才能使用。
- 录制至少一份主视频和一份纯回放备份；准备硬件断电、网络中断、视觉丢失和 UWB 无效时的 Plan B。

**产出：** 演示脚本、视频、PPT 图表、Q&A 资料、证据索引更新。

**通过条件：** 演示步骤可重复、失败时有明确降级；没有把规划目标或测试样例写成实测结果。

## 12. 最终审查与交付

**简要总结：** 交付前检查“能不能复现”和“有没有越界表述”。

**详细解释：**

- 检查 `git status --short` 和 `git diff`，保留其他成员的未提交修改。
- ROS2 代码至少执行 `colcon build`、`colcon test`、`colcon test-result --verbose`；ROS1/bridge 变更补充消息映射、时间和坐标单位验证。
- 检查每张图表、每段视频是否关联运行编号；未验证结果留在实验目录，不进入 `defense/`。
- 单独列出未完成项：例如动态精度未测、真实多相机未接入、ROS2→ROS1 回传未启用等。
- 最终报告区分“已实现”“已测量”“规划目标”“未验证”，不能用“代码已写”代替“精度已达标”。

**产出：** 证据索引、交付清单、未验证项清单、最终版本标签。

**通过条件：** 任何关键结论都能由代码、配置、数据和运行记录复核。

## 推荐的实际排期

### 阶段 A：硬件到货前

完成步骤 1～3：范围、接口契约、ROS2 骨架、离线工具和模拟测试。不做真实精度结论。

### 阶段 B：硬件到货后第 1～2 天

完成步骤 4：硬件验收、接线、载荷安装、桌面通信和安全检查。

### 阶段 C：硬件到货后第 3～5 天

完成步骤 5～6：UWB、视觉、ROS1/ROS2 通道、坐标系、标定和延迟测量。

### 阶段 D：第 2 周

完成步骤 7：执行 E001，锁定可用的单源方案和融合输入。

### 阶段 E：第 3 周

完成步骤 8～9：融合、降级、动态和遮挡/异常实验。

### 阶段 F：第 4 周

完成步骤 10～12：端到端展示、演示录制、答辩材料、证据审查和交付。

## 三条必须坚持的执行原则

1. **先语义，后代码；先基线，后融合。** 不清楚目标是谁、单位是什么、frame 是什么时，不进入精度比较。
2. **先可测量，后优化。** 先保留官方 UWB、单相机视觉等简单基线，再依据真实误差决定是否增加多相机、滤波或更复杂算法。
3. **先记录，后下结论。** 每次实验都保存配置、版本、数据和失败原因；规划中的 5 cm、30 cm 只能作为目标值，不能提前写成结果。
